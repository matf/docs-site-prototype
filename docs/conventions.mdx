# Documentation conventions

How this documentation tree is organised, and where a new page has to be placed so that it
appears in the right position in the navigation.

## One tree, arc42 first

There is exactly one documentation tree, rooted at `Systems`. Beneath every system and every
component the twelve arc42 sections start immediately:

```text
docs/
└── systems/
    └── example-system-a/            → /systems/example-system-a/
        ├── index.mdx                → the system landing page
        ├── 01-introduction-and-goals/
        ├── 02-architecture-constraints.mdx
        ├── …
        ├── 12-glossary.mdx
        └── components/
            └── example-component-a/ → /systems/example-system-a/components/example-component-a/
                ├── index.mdx
                ├── 01-introduction-and-goals.mdx
                └── …
```

Two mechanical rules make this work:

1. **`NN-` prefixes order the navigation** and are stripped from the URL by Docusaurus, so
   `05-building-block-view/` publishes as `…/building-block-view/`. arc42 order is preserved in
   the sidebar and in the previous/next navigation without appearing in any link.
2. **`index.mdx` in a folder becomes that folder's landing page.** That is why a system or a
   component has a useful landing page without a separate `Overview` entry in the sidebar.

An arc42 section that has no child pages is a single file (`02-architecture-constraints.mdx`).
As soon as it needs children it becomes a folder with an `index.mdx` and its child pages next to
it. Nothing else changes — the URL stays the same.

## Where custom documentation goes

Custom documentation is never collected in a catch-all category. It is filed under the arc42
section it semantically belongs to. In most cases that is *8. Crosscutting Concerns*:

| Topic | arc42 section | File |
| --- | --- | --- |
| Security concept | 8. Crosscutting Concerns | `08-crosscutting-concerns/security-and-data-protection.mdx` |
| Operations and monitoring | 8. Crosscutting Concerns | `08-crosscutting-concerns/operations-and-monitoring.mdx` |
| Messaging conventions | 8. Crosscutting Concerns | `08-crosscutting-concerns/integration-conventions.mdx` |
| Stakeholder goal detail | 1. Introduction and Goals | `01-introduction-and-goals/stakeholder-goals.mdx` |
| Operational scenario | 6. Runtime View | `06-runtime-view/failover-and-replay.mdx` |
| Architecture decision record | 9. Architecture Decisions | `09-architecture-decisions/adr-0001-….mdx` |

Adding the `.mdx` file to the folder is sufficient — the sidebar is autogenerated from the
filesystem. Use `sidebar_position` in the frontmatter to place the page among its siblings; this
is how a custom page can sit **between** two generated pages, as
[Integration Conventions](/systems/example-system-a/components/example-component-a/crosscutting-concerns/integration-conventions/)
does.

## Generated, custom and mixed

<ContentLegend />

Each page declares what it is with a single component at the top:

```mdx
<DocHeader
  system="example-system-a"
  component="example-component-a"
  section="runtime-view"
  status="mixed"
  generated={{
    generator: 'bazg-archdoc 0.7.2',
    sourceRepo: 'git.example.admin.ch/bazg-proto/declaration-intake-service',
    revision: '9c1e40d',
    generatedAt: '2026-08-04 03:12 UTC',
  }}
  custom={{owner: 'Team Alpha — Declaration Squad', lastReviewed: '2026-07-30'}}
/>
```

`DocHeader` renders the contextual header (system, component, arc42 section), the status badge
and the provenance panels. Because it reads the system and component catalogue, the names and
teams cannot drift out of sync between pages.

Generated blocks inside a mixed page are always framed with `<Diagram>` or a generated table
component, so the boundary between hand-written explanation and generated output stays visible.

## Expectation for a future generator

The generator is expected to own whole files and to leave everything else alone:

- it writes generated `.mdx` files (context diagrams, component views, message catalogues,
  reaction graphs) and the catalogue data under `src/data/`;
- it never edits a file marked `status="custom"`;
- on a **mixed** page the hand-written prose lives in the page, and the generated part is a
  framed block — a future generator would replace the block, not the page.

Because the information architecture comes from the folder layout and not from a hand-maintained
sidebar file, a generator can add or replace pages without any navigation change.
