## Inherited from the system

All constraints in
[Example System A — 2. Architecture Constraints](/systems/example-system-a/architecture-constraints/)
apply. The ones that shape this component most:

| # | Constraint | Effect here |
| --- | --- | --- |
| O-4 | The inbound message specification is externally fixed. | The intake contract cannot be simplified, only mapped. The anti-corruption mapping lives in the messaging adapter. |
| T-2 | The broker is the only approved asynchronous transport. | No synchronous call to Example Component B, ever. |
| T-3 | Managed relational database only. | The revision history is modelled relationally, with an append-only revision table. |

## Component-specific

| # | Constraint | Reason |
| --- | --- | --- |
| C-1 | The component must accept the full national message specification, including the optional fields nobody uses. | Conformance requirement; unknown-but-declared fields are stored verbatim and passed on. |
| C-2 | Validation rules come from the Tariff and Rules Service and must not be re-implemented locally. | Single source of truth for customs rules. A local copy would drift. |
| C-3 | The component must remain functional with a stale rule cache for at least 24 hours. | The tariff service has a lower availability target than this component. |
| C-4 | No business payload may reach application logs. | Data protection concept; enforced by an architecture test. |

## Consequence

C-2 and C-3 together are why the component has a cached, read-only rule adapter rather than a
rule engine: it must apply somebody else's rules, be honest about their age, and keep working
when the source is down. The trade-off is documented in
[11. Risks and Technical Debt](/systems/example-system-a/components/example-component-a/risks-and-technical-debt/).
