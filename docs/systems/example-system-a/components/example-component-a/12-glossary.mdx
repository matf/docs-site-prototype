| Term | Meaning |
| --- | --- |
| `Declaration` | The aggregate root. Owns its revisions and its state. |
| `Revision` | An immutable snapshot of the declaration content. Numbered from 1. |
| `ACCEPTED` | State after successful validation, before a risk decision exists. |
| `CLEARED` | Terminal state — the consignment may proceed. |
| `HELD` | State while an inspection decision is pending. |
| `REJECTED` | Terminal state — the declaration was not accepted. No revision is created. |
| `outbox` | Table holding events written inside the business transaction, awaiting publication. |
| `processed_message` | Table of handled `messageId` values; the idempotency check. |
| Outbox relay | The workload that publishes rows from `outbox` to the broker. |

</Diagram>

## Terms used carefully

| Term | Note |
| --- | --- |
| **Accepted** | Means "formally valid and stored". It says nothing about risk and nothing about clearance. Declarants read it as "done", which is why the portal wording was reviewed with the specialist unit. |
| **Superseded** | A decision that arrived for a revision that is no longer current. Superseded decisions are discarded, not queued — see [6. Runtime View](/systems/example-system-a/components/example-component-a/runtime-view/). |
| **Rejected** | A business outcome, never a technical failure. A message that cannot be processed is dead-lettered, not rejected. |
