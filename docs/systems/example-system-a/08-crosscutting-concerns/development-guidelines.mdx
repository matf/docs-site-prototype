Rules that apply to every component in this system. Each one exists because breaking it has cost
the team something.

## Component structure

Every component is hexagonal: domain logic in the centre, adapters at the edge.

```text
component/
├── api/            inbound HTTP adapter (thin, no business rules)
├── messaging/      inbound and outbound broker adapters
├── application/    use cases, transaction boundaries
├── domain/         entities, invariants, decisions — no framework imports
└── persistence/    repository implementations
```

The rule that matters: **`domain/` imports nothing from the other folders and nothing from a
framework.** It is enforced by an architecture test in the build, not by review discipline.

## Messaging

- Every consumer is idempotent. Delivery is at-least-once; a redelivered message must not produce
  a second business effect.
- Every published event carries `messageId`, `correlationId`, `causationId`, `occurredAt` and a
  schema version.
- Schema changes are additive within a major version. A breaking change publishes a new major
  channel and both run in parallel until consumers have migrated.
- The concrete conventions and header set are documented per component — see
  [Integration Conventions](/systems/example-system-a/components/example-component-a/crosscutting-concerns/integration-conventions/).

## Persistence

- One database schema per component, no cross-component reads.
- State changes and outgoing events are written in the same transaction using the outbox pattern —
  [ADR-0001 of Example Component A](/systems/example-system-a/components/example-component-a/architecture-decisions/adr-0001-transactional-outbox/).
- Migrations are forward-only and must be deployable while the previous version is still running.

## Logging

- No business payloads in logs. Fields annotated as sensitive are refused by the serialiser.
- Every log line carries the `correlationId`, so a declaration can be followed across components.
- Log levels: `ERROR` means somebody must act; `WARN` means somebody should look during office
  hours. Anything else is `INFO` or lower.

## Testing

| Level | Scope | Gate |
| --- | --- | --- |
| Unit | Domain logic, no infrastructure | Every build |
| Contract | Published and consumed message schemas | Every build; consumer contracts run against the producer |
| Integration | Component with real broker and database in containers | Every build |
| Architecture | Layering rules, logging annotations | Every build |
| Load | Peak profile against `staging` | Before each release |

## Documentation

Documentation follows the same lifecycle as the code. A component's generated pages are
regenerated on every merge to `main`; its custom pages are reviewed at least every six months and
carry the review date. See [Documentation conventions](/conventions/).
