This section holds the concepts that no single component owns. It is also the section most
custom documentation ends up in: security concepts, operating procedures, engineering guidelines
and integration conventions all belong here rather than in a generic catch-all category.

## Concepts documented for this system

| Concept | Page | Content |
| --- | --- | --- |
| Security and data protection | [Security and Data Protection](/systems/example-system-a/crosscutting-concerns/security-and-data-protection/) | <StatusBadge status="custom" small /> |
| Operations and monitoring | [Operations and Monitoring](/systems/example-system-a/crosscutting-concerns/operations-and-monitoring/) | <StatusBadge status="custom" small /> |
| Development guidelines | [Development Guidelines](/systems/example-system-a/crosscutting-concerns/development-guidelines/) | <StatusBadge status="custom" small /> |
| Concept coverage | [Concept Coverage](/systems/example-system-a/crosscutting-concerns/concept-coverage/) | <StatusBadge status="generated" small /> |

Component-specific crosscutting concepts are documented on the component, not here. Message
contracts are the exception in the other direction: they are defined by the *system*, so they live
under [5. Building Block View](/systems/example-system-a/building-block-view/) rather than on any
component.

The last row is generated: which component actually applies which concept is collected from the
component repositories rather than asserted here. That page is overwritten on every generation
run, which is why it is a page of its own and not a table on this one.

## How to add a concern here

Drop an `.mdx` file into `docs/systems/example-system-a/08-crosscutting-concerns/` and it appears
in this list. Use `sidebar_position` to place it among its siblings. If a topic fits another
arc42 section better — an operational scenario, for instance — it belongs there instead, under
*6. Runtime View*. See [Documentation conventions](/conventions/).
