Component-level refinements of
[Example System A — 10. Quality Requirements](/systems/example-system-a/system-architecture/quality-requirements/).

| # | Quality | Stimulus | Response | Measure |
| --- | --- | --- | --- | --- |
| CB-1 | Reproducibility | A three-year-old decision is recomputed with its recorded rule set and model version. | The same band and the same fired rules. | Byte-identical decision payload, verified in the semi-annual audit rehearsal. |
| CB-2 | Determinism | The same case is evaluated twice in the same process and in two different processes. | Identical result. | Property-based test in every build. |
| CB-3 | Changeability | A new rule set is published. | It becomes effective without a deployment. | Effective within 5 minutes; the version appears in every subsequent decision. |
| CB-4 | Availability of decisions | The Model Registry is unavailable and the active model is not cached. | The fallback rule set decides; the decision is marked as fallback. | No revision is left without a decision; `risk_fallback_ratio` visible within 1 minute. |
| CB-5 | Throughput | A 30-minute backlog of declaration events. | The backlog drains. | Drained within 20 minutes at 16 replicas. |
| CB-6 | Fairness | A model is proposed that uses declarant identity directly. | The build fails. | Architecture test over the feature set; verified in every build. |
| CB-7 | Explainability | A customs officer opens a held consignment. | The decision names every rule that fired and the band boundary. | Every `RiskAssessmentCompleted` carries `firedRules[]`, `score`, `band`, `ruleSetVersion`, `modelVersion`. |

## Verification

| Scenario | Verified by |
| --- | --- |
| CB-1 | Semi-annual audit rehearsal against archived cases |
| CB-2, CB-6 | Automated tests in every build |
| CB-3 | Integration test with a registry double |
| CB-4 | Chaos test — the registry is blocked at the egress proxy |
| CB-5 | Load test against `staging` before each release |
| CB-7 | Contract test over the decision schema |
