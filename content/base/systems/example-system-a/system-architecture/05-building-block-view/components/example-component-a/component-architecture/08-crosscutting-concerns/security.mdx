This page describes what is specific to this component. The classification, retention and
authorisation model are defined once for the system in
[Security and Data Protection](/systems/example-system-a/system-architecture/crosscutting-concerns/security-and-data-protection/)
and are not repeated here.

## Trust boundaries

| Boundary | What crosses it | Control |
| --- | --- | --- |
| Broker → messaging adapter | Commands from the trade portal | mTLS on the broker; the portal's signature over the command payload is verified before the command is accepted |
| API adapter → application service | Officer queries, operator admin calls | OIDC token validated, role checked, then re-checked in the application service |
| Rule client → egress proxy | Tariff lookups | Allow-listed destination, no credentials in the request, response schema validated |
| Persistence adapter → database | Declaration payloads | Encrypted at rest by the managed service; credentials rotated by the platform |

The signature verification is the load-bearing control: it is what makes a forged
`SubmitDeclaration` on the broker useless even if a producer credential leaks.

## Authorisation enforced by this component

| Role | Endpoint / operation | Allowed |
| --- | --- | --- |
| `declarant` (via portal) | Submit, correct own declarations | Own declarations only, enforced by the declarant identity in the signed command |
| `customs-officer` | `GET /declarations/{id}` | Read any declaration, including hold reasons |
| `risk-analyst` | — | No access to this component's API |
| `operator` | `POST /internal/replay`, `GET /internal/state` | Technical metadata only; no payload access |

The `operator` row is the one that gets questioned in every review. An operator can replay a
dead-lettered message by its identifier and can see counts and states, but the endpoint never
returns a declaration payload. That is what makes the recovery procedure in
[Failover and Replay](/systems/example-system-a/system-architecture/building-block-view/components/example-component-a/component-architecture/runtime-view/failover-and-replay/)
executable without a data protection exception.

## Secrets

Nothing in the component's own configuration is a secret. Database credentials and the broker
client certificate are platform-managed secrets, mounted at runtime and rotated every 90 days —
see the generated configuration surface in
[7. Deployment View](/systems/example-system-a/system-architecture/building-block-view/components/example-component-a/component-architecture/deployment-view/).
The component fails its readiness probe rather than starting with a missing secret.

## Logging and data protection

Fields annotated as sensitive in the domain model are refused by the log serialiser: an attempt
to log one fails the build's architecture test rather than leaking at runtime. The generated
[Observability](/systems/example-system-a/system-architecture/building-block-view/components/example-component-a/component-architecture/crosscutting-concerns/observability/)
inventory is the evidence — every listed log event carries identifiers and rule codes, never a
payload.

## Open points

| # | Point | Status |
| --- | --- | --- |
| S-1 | Signature verification uses a single portal key; key rotation requires a coordinated deployment. | Accepted for now; multi-key support planned. |
| S-2 | Admin API access is logged but not separately alerted. | Alert planned with the next observability increment. |
