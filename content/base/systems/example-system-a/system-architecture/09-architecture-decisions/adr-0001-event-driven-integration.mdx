# ADR-0001 — Event-driven integration between components

## Context

Example System A must stay available for declaration intake during opening hours, and every
clearance decision must be reconstructable for ten years. The two components — declaration intake
and risk assessment — have different load profiles and different failure characteristics: intake
is latency-sensitive and simple, risk assessment is compute-heavy and changes often.

A synchronous design was on the table: intake calls the risk engine and waits. It is simpler to
build, simpler to test and simpler to explain.

## Decision

Components integrate exclusively through **durable business events on the central message
broker**. No component calls another component synchronously. Events are versioned, immutable and
retained for the legal retention period; the event log is the audit record.

## Consequences

**Positive**

- Intake stays available when risk assessment is down. Declarations accumulate as `ACCEPTED` and
  are decided when the engine recovers — see
  [Peak Load and Degradation](/systems/example-system-a/system-architecture/runtime-view/peak-load-and-degradation/).
- The ten-year reconstruction requirement is satisfied by the event log itself rather than by a
  parallel audit write path.
- The two components scale independently, which matters because their load profiles differ by an
  order of magnitude.

**Negative**

- The declaration state is eventually consistent. A declarant can see `ACCEPTED` for a while
  before seeing `CLEARED`, and the trade portal had to be changed to show that honestly.
- Every consumer must be idempotent, because delivery is at-least-once. This is a permanent tax on
  every new consumer — implemented via the transactional outbox in
  [ADR-0001 of Example Component A](/systems/example-system-a/components/example-component-a/system-architecture/architecture-decisions/adr-0001-transactional-outbox/).
- Operations needs a replay procedure and the training to use it —
  [Failover and Replay](/systems/example-system-a/components/example-component-a/system-architecture/runtime-view/failover-and-replay/).
- Debugging a single declaration means correlating across components, which is why
  `correlationId` propagation is mandatory in the
  [Development Guidelines](/systems/example-system-a/system-architecture/crosscutting-concerns/development-guidelines/).

## Alternatives considered

| Alternative | Why not |
| --- | --- |
| Synchronous REST call from intake to risk assessment | Couples the availability of intake to the risk engine, and leaves no durable decision record. |
| Shared database between the components | Removes the ownership boundary; a risk engine change would be able to break intake. Rejected outright. |
| Events plus a synchronous fast path for low-risk cases | Two code paths for the same decision, two failure modes, two things to audit. The latency budget did not require it. |
