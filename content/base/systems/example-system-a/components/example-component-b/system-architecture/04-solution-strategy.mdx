## Four decisions that shape the component

| Approach | Addresses | Where |
| --- | --- | --- |
| **Rule sets and models as immutable versioned artefacts**, referenced by version in every decision. | Reproducibility, changeability | [ADR-0001](/systems/example-system-a/components/example-component-b/system-architecture/architecture-decisions/adr-0001-versioned-rule-sets/) |
| **Deterministic evaluation.** No wall-clock, no randomness, no ambient state in the scoring path. | Constraint CB-1 | [5. Building Block View](/systems/example-system-a/components/example-component-b/system-architecture/building-block-view/) |
| **Risk case per revision.** The case, not the declaration, is the unit of work; a new revision opens a new case. | Correctness under corrections | [6. Runtime View](/systems/example-system-a/components/example-component-b/system-architecture/runtime-view/) |
| **Conservative fallback.** If the scoring model is unavailable, a versioned fallback rule set decides — never silence. | Constraint CB-4 | Below |

## Why a case per revision

A correction invalidates the previous assessment. Modelling the case per *declaration* would
require mutating an existing decision, which breaks reproducibility. Modelling it per *revision*
makes each decision a fact about an immutable input — and lets
[Example Component A](/systems/example-system-a/components/example-component-a/) discard
decisions for superseded revisions without any coordination between the two components.

## The fallback, and why it is not silent

If the scoring model cannot be loaded, the component evaluates the fallback rule set: a small,
deterministic, analyst-maintained rule set that errs towards `elevated`. Every fallback decision
is marked as such in the event, and the fallback rate is a monitored metric.

The alternative — waiting for the model and producing no decision — was rejected because a
missing decision leaves a consignment in `ACCEPTED` indefinitely, and nobody notices until a
haulier calls.
