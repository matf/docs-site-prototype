## Inherited from the system

All constraints in
[Example System A — 2. Architecture Constraints](/systems/example-system-a/system-architecture/architecture-constraints/)
apply. The decisive ones:

| # | Constraint | Effect here |
| --- | --- | --- |
| O-2 | Decisions are subject to legal review for ten years. | Rule set and model versions are part of every decision event; neither may ever be deleted. |
| O-3 | Rule sets are owned by the specialist unit. | Rules are data, published by analysts, not code deployed by engineers. |
| T-2 | Broker-only asynchronous transport. | The component is a pure consumer/producer; it exposes no business API. |

## Component-specific

| # | Constraint | Reason |
| --- | --- | --- |
| CB-1 | Scoring must be deterministic: the same inputs, rule set version and model version always produce the same band. | Reproducibility goal. Rules out anything with runtime randomness or wall-clock-dependent behaviour. |
| CB-2 | No model may use the declarant's identity as a direct feature. | Legal and fairness requirement; identity may only enter through aggregated history features that are reviewed. |
| CB-3 | Rule sets and models are immutable once published; a change is a new version. | Makes rollback a one-step operation and keeps history reproducible. |
| CB-4 | A decision must be produced for every revision, even when the model is unavailable. | A missing decision blocks a consignment; the fallback is a conservative band, never silence. |

CB-1 and CB-4 pull against each other: determinism argues for one code path, availability argues
for a fallback. The resolution — a versioned fallback rule set that is itself deterministic — is
described in
[4. Solution Strategy](/systems/example-system-a/components/example-component-b/system-architecture/solution-strategy/).
