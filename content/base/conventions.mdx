# Documentation conventions

How this documentation tree is organised, and where a new page has to be placed so that it
appears in the right position in the navigation.

  owner="Architecture Documentation Team (fictional)"
  lastReviewed="2026-07-28"

/>

## One tree, with a documentation structure level

There is exactly one documentation tree, rooted at `Systems`. Beneath a system or a component sits
the **documentation structure** — the methodology the documentation follows — and beneath that its
sections start immediately:

| Structure | Methodology | URL segment | Applies to |
| --- | --- | --- | --- |
| System Architecture — **Component Architecture** below a component | arc42 | `system-architecture` | systems and components |
| Specification Docs | BMAD | `specs-docs` | systems |

The arc42 structure is displayed as *System Architecture* below a system and as *Component
Architecture* below a component: it is the same methodology describing a different thing. The URL
segment stays `system-architecture` in both cases, so the label can change without breaking a
single link.

An entity can carry several structures at once. [Example System A](/systems/example-system-a/) has
both; everything else in this prototype has only a System Architecture, and structures with no
content are not shown.

Adding a methodology means adding an entry to `src/data/structures.ts` and a folder in the content
tree. Nothing in the navigation code changes.

```text
content/base/
└── systems/
    └── example-system-a/                → /systems/example-system-a/
        ├── index.mdx                    → the system landing page
        ├── system-architecture/         → /systems/example-system-a/system-architecture/
        │   ├── _category_.json
        │   ├── index.mdx
        │   ├── 01-introduction-and-goals/
        │   ├── 02-architecture-constraints.mdx
        │   └── …
        ├── specs-docs/                  → /systems/example-system-a/specs-docs/
        │   ├── _category_.json
        │   ├── index.mdx
        │   ├── 01-project-brief.mdx
        │   └── …
        └── components/
            └── example-component-a/     → /systems/example-system-a/components/example-component-a/
                ├── index.mdx
                └── system-architecture/
                    ├── index.mdx
                    ├── 01-introduction-and-goals.mdx
                    └── …
```

Two mechanical rules make this work:

1. **`NN-` prefixes order the navigation** and are stripped from the URL by Docusaurus, so
   `05-building-block-view/` publishes as `…/building-block-view/`. arc42 order is preserved in
   the sidebar and in the previous/next navigation without appearing in any link.
2. **`index.mdx` in a folder becomes that folder's landing page.** That is why a system or a
   component has a useful landing page without a separate `Overview` entry in the sidebar.

An arc42 section that has no child pages is a single file (`02-architecture-constraints.mdx`).
As soon as it needs children it becomes a folder with an `index.mdx` and its child pages next to
it. Nothing else changes — the URL stays the same.

## Where custom documentation goes

Custom documentation is never collected in a catch-all category. It is filed under the arc42
section it semantically belongs to. In most cases that is *8. Crosscutting Concerns*:

| Topic | Structure and section | File below the structure folder |
| --- | --- | --- |
| Security concept | System Architecture → 8. Crosscutting Concerns | `08-crosscutting-concerns/security-and-data-protection.mdx` |
| Operations and monitoring | System Architecture → 8. Crosscutting Concerns | `08-crosscutting-concerns/operations-and-monitoring.mdx` |
| Messaging conventions | System Architecture → 8. Crosscutting Concerns | `08-crosscutting-concerns/integration-conventions.mdx` |
| Stakeholder goal detail | System Architecture → 1. Introduction and Goals | `01-introduction-and-goals/stakeholder-goals.mdx` |
| Operational scenario | System Architecture → 6. Runtime View | `06-runtime-view/failover-and-replay.mdx` |
| Architecture decision record | System Architecture → 9. Architecture Decisions | `09-architecture-decisions/adr-0001-….mdx` |
| Requirement detail | Specification Docs → 2. Product Requirements | `02-product-requirements/functional-requirements.mdx` |

Adding the `.mdx` file to the folder is sufficient — the sidebar is autogenerated from the
filesystem. Use `sidebar_position` in the frontmatter to place the page among its siblings; this
is how a custom page can sit **between** two generated pages, as
[Integration Conventions](/systems/example-system-a/components/example-component-a/system-architecture/crosscutting-concerns/integration-conventions/)
does.

## One tree per environment

The documentation is published four times, once per environment:

| Environment | Route | Reflects |
| --- | --- | --- |
| DEV | `/dev/…` | HEAD of every component repository |
| REF | `/ref/…` | The integration baseline |
| ABN | `/abn/…` | The release candidate under acceptance |
| PROD | `/…` | The released revision running in production |

Production is served at the root, so its URLs are the canonical ones and never change. Every tree
describes the state of its own environment — which components are deployed, which revision each
page was generated from, which version a contract is at. There is deliberately no diff view: to
compare, switch environments and look.

Pages are authored **once**. `content/base/` is shared by every environment and
`content/overrides/<env>/` holds what differs there; `npm run prepare-docs` composes the four trees
into `docs-build/`, which is generated and never edited. A file that exists only in an override
exists only on that environment — that is how *Example Component D* is on DEV and nowhere else.

A shared page therefore **cannot link to an environment-specific page**: the link would be broken
in every other tree. The build enforces this, because broken links fail it. If a shared page needs
to point at something that only exists somewhere, it needs an override of its own — or the link
belongs in a component that can check whether the target exists.

Because pages are shared, their links are written environment-relative (`/systems/…`). Two
mechanisms add the prefix: a remark plugin for Markdown links, and the `EnvLink` component for
everything rendered from JSX. No author and no generator has to think about it.

## Generated or custom — never both

<ContentLegend />

There is no third value. A page has exactly one origin, declared once in its frontmatter:

```yaml
---
title: 6. Runtime View
sidebar_label: 6. Runtime View
sidebar_position: 0
doc_status: generated      # or: custom
---
```

Every page below a structure also names it, so the contextual header and the breadcrumbs can show
where the reader is:

```mdx
<DocHeader structure="system-architecture" system="example-system-a" section="runtime-view" … />
```

`doc_status` is the single source of truth. `<DocHeader>` reads it to render the badge, and the
build-time `bazg-doc-status` plugin reads it to build the navigation — which is why the sidebar,
the section lists and the page counts can never disagree with the page itself.

```mdx
<DocHeader
  system="example-system-a"
  component="example-component-a"
  section="runtime-view"
  generated={{
    generator: 'bazg-archdoc 0.7.2',
    sourceRepo: 'git.example.admin.ch/bazg-proto/declaration-intake-service',
    revision: '9c1e40d',
    generatedAt: '2026-08-04 03:12 UTC',
    scope: 'Whole page — reaction graph and reaction table',
  }}
/>
```

### When a generated artefact needs explanation

Write a second page. The generated artefact keeps the arc42 section route; the hand-written
explanation becomes a custom page directly beneath it:

```text
system-architecture/05-building-block-view/
├── index.mdx           doc_status: generated   the component view
└── design-notes.mdx    doc_status: custom      why it is shaped that way
```

This is what makes regeneration safe: the generator replaces whole files and never has to merge
into somebody's prose. A page that would be "half generated" is two pages.

## Events and commands belong to the system

A message contract is not owned by the component that happens to publish it. Several components
produce and consume the same contract, and the contract outlives any of them, so it is documented
**per system** — one page per event or command, directly below the system's System Architecture
*5. Building Block View*. That is the section that describes how the building blocks fit together,
which is exactly what the messages between them are.

```text
content/base/systems/example-system-a/system-architecture/05-building-block-view/
├── _category_.json
├── index.mdx                        the component diagram + the contract catalogue
├── decomposition-rationale.mdx      custom
├── submit-declaration.mdx           one page per command …
├── correct-declaration.mdx
├── declaration-accepted.mdx         … and one per event
└── …
```

Commands come first, then events, ordered by `sidebar_position`. Each page is fully generated from
the contract definition: producer, consumers, channel, schema and version, ordering key, retention,
the payload fields, an example and the version history.

A component page never repeats the contract. It shows only *which* of the system's messages it
consumes and publishes, on its own *5. Building Block View*, with every name linking to the
contract page. In prose, `<Msg system="example-system-a" name="DeclarationAccepted" />` renders an
inline link to it.

## Sections only exist when they have content

The twelve arc42 sections are a checklist, not a quota. A section that has nothing to say does
not get a placeholder page — it simply does not exist, and the navigation does not show it.

A component always has *3. Context and Scope*, *5. Building Block View* and *6. Runtime View*:
those three say what it is and what it does, and all three are generated. Everything else appears
only when the component has its own content for it.

[Example System B](/systems/example-system-b/) documents nine of twelve sections and
[Example Component C](/systems/example-system-b/components/example-component-c/) five of twelve.
The gaps in the numbering are the only sign that a section is missing — which is exactly the
intent. Deleting a section file removes it from the navigation; nothing else has to be updated.

## Expectation for a future generator

The generator is expected to own whole files and to leave everything else alone:

- it writes generated `.mdx` files (context diagrams, component views, message catalogues,
  reaction graphs) and the catalogue data under `src/data/`;
- it never edits a file whose frontmatter says `doc_status: custom`;
- it may delete a generated page when the artefact behind it disappears — the section then stops
  appearing in the navigation, which is the correct outcome.

Because the information architecture comes from the folder layout and not from a hand-maintained
sidebar file, a generator can add or replace pages without any navigation change.
